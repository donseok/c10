## 3. 워크플로우

### 3.1 초기화 — 팀모드 (최초 1회)

1. tmux 실행 여부 확인 → 미실행 시 솔로모드(3.2로 직행)
2. TeamCreate → 팀 생성
3. 분석팀원1~{TEAM_SIZE} 스폰 (업무 미할당, 대기) → monitor 최후 스폰 (active pane 확보)
4. `/usage-monitor start` → 사용량 확인
5. `normal`(<90%) → 최대 {TEAM_SIZE}명에게 각 1건씩 할당 / `stop`(≥90%) → 전원 대기, 리셋 후 재확인

**스폰 시 프롬프트 템플릿:**
```
C10 레거시 서비스 분석팀원입니다.
팀리더(team-lead)의 SendMessage 지시를 대기하세요.
지시 없이 스스로 작업을 시작하지 마세요.
```

**업무 할당 SendMessage 템플릿:**
```
반드시 Skill 도구를 사용하여 /analyze-service 스킬을 호출하세요:
  Skill(skill="analyze-service", args="{SERVICE_ID}")
직접 파일을 읽어서 수동 분석하지 마세요. 반드시 Skill 도구로 스킬을 실행해야 합니다.
완료 후 SendMessage로 팀리더(team-lead)에게 보고하고, 다음 지시가 올 때까지 대기하세요.
추가 서비스를 스스로 시작하지 마세요.
```

**⚠️ 스킬 사용 강제 (필수)**:
- 분석은 **반드시 Skill 도구로 `/analyze-service` 스킬을 호출**하여 수행한다
- 스킬 없이 직접 파일을 읽어 수동으로 보고서를 작성하면 **경로·파일명·문서 형식이 모두 달라져서 실패**한다
- 올바른 방법: `Skill(skill="analyze-service", args="SERVICE_ID")`
- 잘못된 방법: 서비스 XML/쿼리/JSP를 직접 읽어서 마크다운 보고서를 수동 작성
- 스킬이 Phase 1~5 파이프라인을 거쳐 `docs/analysis/service/[ui|nui]/{ID}_legacy_analysis.md` 경로에 표준 형식 문서를 자동 생성한다

### 3.2 분석 반복

**상태**: ⬜ 미분석(할당 가능) → 🔄 분석 중(중복 할당 금지) → ✅ 완료

**매 iteration:**
1. 체크리스트 읽고 ⬜ 확인. ✅/🔄 건너뜀. 전부 ✅이면 종료(4.4)
2. ⬜ 서비스 **1건** 선택 → 즉시 🔄 마킹
   - **챕터 분산**: 팀원별로 서로 다른 챕터(### 절)를 우선 할당
3. 완료 보고(SendMessage) 수신 → **산출물 검증(3a)** → 🔄→✅ 갱신 → 요약 테이블 +1
4. **컨텍스트 초기화** (아래 명령어를 Bash 도구로 **한 글자도 변경 없이** 실행):
   ```bash
   tmux send-keys -t {paneId} '/clear' && sleep 10 && tmux send-keys -t {paneId} Enter && sleep 10 && tmux send-keys -t {paneId} Enter
   ```
   - `/clear`와 `Enter`는 **별도 send-keys로 분리** (합치면 실패)
   - `{paneId}`: 팀원의 tmux pane ID (예: `%14`). 종료 알림의 `paneId` 필드에서 확인
   - SendMessage로 /clear 보내기 금지
5. 초기화 완료 후 **SendMessage로 다음 ⬜ 1건 할당**
6. 실패 시 🔄→⬜ 복원. 컨텍스트 한계까지 **멈추지 않고** 반복

#### 3a. 산출물 검증 (✅ 마킹 전 필수)

스킬이 재귀 호출(/analyze-custom-class, /analyze-plsql)로 **할당된 서비스 외에 추가 문서**를 생성할 수 있다. ✅ 마킹 전에 실제 생성된 산출물을 검증한다.

```bash
# 1) 메인 분석 문서 확인
ls docs/analysis/service/ui/{SERVICE_ID}_legacy_analysis.md docs/analysis/service/nui/{SERVICE_ID}_legacy_analysis.md 2>/dev/null

# 2) 중간 JSON 산출물 확인
ls docs/analysis/service/ui/.temp/{SERVICE_ID}_*.json docs/analysis/service/nui/.temp/{SERVICE_ID}_*.json 2>/dev/null

# 3) 재귀 호출로 생성된 부가 문서 확인 (sql_analysis.json 기반)
python3 -c "
import json, os, glob
# sql_analysis.json 찾기
for p in glob.glob('docs/analysis/service/*/.temp/{SERVICE_ID}_sql_analysis.json'):
    data = json.load(open(p))
    # PL/SQL 분석 보고서 확인
    plsql = data.get('plsqlCalls', {})
    for call in plsql.get('detectedCalls', []):
        rp = call.get('reportPath', '')
        status = '✅' if rp and os.path.exists(rp) else '❌ 누락'
        print('PL/SQL: %s → %s' % (call.get('fullCall', '?'), status))
    if not plsql.get('detectedCalls'):
        print('PL/SQL: (없음)')

# 커스텀 클래스 분석 보고서 확인
for p in glob.glob('docs/analysis/service/*/.temp/{SERVICE_ID}_java_analysis.json'):
    data = json.load(open(p))
    for cls in data.get('customClasses', []):
        name = cls.get('className', '?')
        report = 'docs/analysis/service/customClass/%s_class_analysis.md' % name
        status = '✅' if os.path.exists(report) else '❌ 누락'
        print('CustomClass: %s → %s' % (name, status))
"
```

- **전부 ✅** → 🔄→✅ 마킹
- **❌ 누락 항목 있음** → 체크리스트 비고란에 누락 항목 기록, 🔄→✅ 마킹은 진행 (재귀 산출물 누락으로 메인 분석을 재실행하지 않음)
- **메인 문서(`_legacy_analysis.md`) 자체가 없음** → 🔄→⬜ 복원 (실패 처리)

**1건씩 할당 원칙**: 스폰 시에도, 후속 할당 시에도 **항상 1건만**. 복수 할당 시 팀리더 통제 불가.

**품질 요구사항**: SQL(목적·테이블관계·바인드변수·컬럼 상세, 비즈니스 의미 해석) | UI(레이아웃+이벤트핸들러+데이터흐름) | Java 없으면 '없음' 명시 | E2E 데이터흐름 다이어그램 | 특이 로직 별도 강조

## 4. 팀모드 규칙

### 4.1 팀 구성

| 역할 | name | 설명 |
|------|------|------|
| 팀리더 | team-lead | 전체 관리, 업무 분배, 사용량 확인 |
| 분석팀원1~{TEAM_SIZE} | 분석팀원1~{TEAM_SIZE} | 팀리더 지시에 따라 분석·보고 |
| monitor | monitor | 사용량 조회용 pane (최후 스폰) |

**신규 팀원 생성 금지** — 병렬 처리 필요 시 팀원 내부에서 Task 도구(서브에이전트) 사용.

### 4.2 사용량

- `normal`(<90%) → 최대 {TEAM_SIZE}명 할당 / `stop`(≥90%) → 신규 할당 중단, 팀원은 대기 유지(소집해제 금지), 리셋 후 재개
- 스킬: `/usage-monitor start`, `/usage-monitor check`

### 4.3 행동 규칙

- 팀리더는 **이벤트 기반** — SendMessage 수신으로 반응. **sleep+capture-pane 폴링 금지**
- capture-pane 허용: 10분 이상 무응답(장애 의심), 프로세스 생존 확인, 디버깅 시만
- 상태 확인: TaskList 조회
- 팀원 소집해제는 **최종 종료 시에만** (사용량 조절 목적 해제 금지)

### 4.4 SendMessage 중복 전송 금지 (필수)

- **idle 알림은 정상 동작**이다. 팀원이 스폰 직후 idle 상태가 되는 것은 SendMessage 수신 대기 상태이므로, 이미 전송한 할당 메시지를 **절대 재전송하지 않는다**
- SendMessage는 **inbox 큐** 방식이다. 같은 메시지를 2번 보내면 큐에 2건이 쌓이고, 팀원은 완료 후 두 번째 메시지를 꺼내 **동일 서비스를 재실행**한다
- 재실행된 서비스는 캐시 히트로 빠르게 끝나지만, **컨텍스트와 시간을 낭비**하고 팀리더의 상태 추적을 혼란시킨다
- /clear 후에도 inbox 잔여 메시지는 **삭제되지 않는다**. /clear는 대화 컨텍스트만 초기화하며, inbox 큐의 미처리 메시지는 그대로 남아 순서대로 소비된다
- **올바른 흐름**: 1건 할당 → 완료 보고 수신 → 검증·✅ 마킹 → /clear → 다음 1건 할당 (이전 할당을 절대 반복하지 않음)
- **팀원이 작업 중일 때 /clear 금지**: 완료 보고를 받기 전에 /clear를 보내면 진행 중인 작업이 중단된다. 반드시 **완료 보고 수신 후** /clear를 실행한다

### 4.5 종료

모든 팀원 shutdown_request → `/usage-monitor stop` → TeamDelete(선택) → 최종 체크리스트 확인
